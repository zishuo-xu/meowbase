# 待批卡聚到一页

一篇只写**一个**可验收的特性。写完就做这一篇,做完再开下一篇。不要在这里预写路线图。

开篇先想:同一问题他们公开怎么设计,这一篇能靠多近。能靠就靠;本篇没更近,写清差在哪、为什么先薄。不读、不抄源码。

- 状态:`已落地`
- 对照 clowder:F246 审批中心——人不必翻进某条线程才看得见待批;Hub 是拉式收件箱。
- 靠拢:拿「全局待批列表 + 能在这一页批/打回 + 能跳进线程」。差在多来源适配器和推送:本篇只聚合现有审批卡。

## 门（各一句）

- **功能**：Hub 有「待批」页,列出所有还没落地的卡:哪条线程、谁写谁审、改动一句。可以批准、打回,或点进那条线程。
- **价值**：人在线程 A 时,线程 B 的卡不会漏。面试能指着一页讲「人握合并权」。
- **愿景**：仍是邮差。这一页是待签收的信封堆,不新开第二套审批。
- **落点**：现有 `GET /api/approvals`(不带 threadId);Hub 一页;点进线程走现有 `onSelect`。

## 为什么

卡散在各条时间线里。对照他们:人会问「我没看那条线程呢?」。喵窝差的是聚合。不做成 X:简历讲审批,演示时还得猜哪条线程亮了点。

不另建提案表。没有卡就不出现。已落地 / 打回 / 作废进历史段,很淡。

## 怎么做

1. `pendingApprovals(cards)` 抽出 draft / reviewing / approved。
2. Hub 侧栏「待批」,打开拉 `listApprovals()`。一条一行:线程标题、写/审、diffStat 一句、批准/打回/去看。
3. 批准发 `#approve id`,打回发 `#reject id 理由`,走现有 `sendMessage`。去看关闭 Hub 并选中线程。
4. 空态:「没有待批的卡」。
5. 验收:两条线程各一张 reviewing → Hub 待批看见两行;点批准走现有命令。

## 不做（本篇）

- 推送、批量、按功能过滤
- 把所有跨线程通讯变成审批
- 新的审批状态机

## 入口

- 过滤:`packages/web/lib/approvals.ts` `pendingApprovals`
- Hub 页:`packages/web/components/TeamHub.tsx` 待批
- 接线:`packages/web/app/page.tsx` 批准/打回走 `#approve` / `#reject`,去看选中线程
