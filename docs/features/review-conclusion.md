# 只认真正的结论段

一篇只写**一个**可验收的特性。写完就做这一刀，做完再开下一篇。不要在这里预写路线图。

开篇先想：同一问题他们公开怎么设计，这一刀能靠多近。能靠就靠；本刀没更近，写清差在哪、为什么先薄。不读、不抄源码。

- 状态:`已落地`
- 对照 clowder:公开语义是「审查结论就是出口」——结论必须明确写通过 / 需修改，平台按结论决定球权和落地。怎么从一段自由文本里认出结论段，是实现细节，他们没公开。
- 靠拢:语义一字不改，仍只认「通过 / 需修改」两个出口。这一刀只把「哪一段才算结论段」读对，不新增关键词、不放宽验证闸。

## 门（各一句）

- **功能**：审查官按 `skills/prompts/review.md` 的格式写（开头「审查结论:」小标题 + 文末「结论:通过」），平台读得对
- **价值**：不白补问一次，也不会把「需修改」读成通过
- **愿景**：邮差照原话记结论，不替审查官改判
- **落点**：`shared/src/review-verdict.ts` 的 `extractConclusion`；web 两处镜像跟齐

## 为什么

浏览器真实跑里闪闪第一跳已经写了 `**结论:通过**`，平台还是发了「出口未明」再问一次：多一跳模型钱、聊天里多一条重复审查气泡。

根因是抽结论段的正则里 `结论\s*[:：]\s*([^\n]+)` 的 `\s*` 会跨行，且取**第一个**「结论」。回复开头那句当小标题用的「审查结论:」于是劫走匹配，捕获到下一行的 `**问题列表**`——一个关键词都没有。

补问只是花钱。真危险的是同一个函数喂给 `parseReviewVerdict`，而它**一个关键词都没匹配到时默认 pass**：审查官把「结论:」写在开头当标题、把「需修改」写在正文，平台会读成通过。这一跳的通过还会往下喂 `gateReviewVerdict` 和 `allowsAutoApprove`。这次没出事只是运气——文末那句正好写了「通过」。

同一片还有第二颗雷：`需修改` 的正则会吃掉「**无**需修改」。这次「通过」正好出现在「无需修改」之前，靠「取先出现的」侥幸判对；写成「改动无需修改，通过」就会翻成需修改。

## 怎么做

1. 抽结论段改成收集**所有**候选段（`#`/`**` 包的独占一行 结论小标题 → 取其后全文；行内 `结论:` → 取**同一行**剩下的，分隔符两侧只许空格和制表符，不许跨行）。
2. 候选里取**最后一个带出口关键词的**。真结论通常在末尾；开头那句「审查结论:」正是假阳性。
3. 一个候选都没关键词 → 仍回退全文，`parseReviewVerdict` 的默认 pass 不动。护栏是「读对结论段」，不是改默认。
4. `需修改` 前面是「无 / 不 / 如」的不算需修改。
5. web 刻意不依赖 `shared`，同一规则在仓库里有三份拷贝。web 那两份收进 `packages/web/lib/review-conclusion.ts` 一处，跟 `shared` 保持镜像。
6. 验收：把真实那段（开头「审查结论:」+ 文末「**结论:通过**」）喂进去 → 不补问、顶栏球回人、卡片标题「审查通过」；同一形状但文末写「需修改」→ 判 revise。

## 不做（本篇）

- 不把「无需修改」当通过的同义词
- 不动验证闸（没证据仍不算通过）
- 不让 web 依赖 `shared`（三份拷贝合成两份就停）

## 入口

- `extractConclusion` / `REVISE_RE`：`packages/shared/src/review-verdict.ts`
- web 镜像：`packages/web/lib/review-conclusion.ts`，被 `ball.ts`（顶栏球权）和 `parse-message.ts`（卡片标题）用
- 补问是否发出：`shouldNudgeExit`（`packages/shared/src/a2a.ts`），见 [exit-nudge.md](exit-nudge.md)
